### 守らないといけないこと3つ

**1. 同時に掲載できるのは 100 曲まで。**
これは料金区分そのもので、超えた時点で許諾の範囲外。**draft は何曲持っていてもよい**
(枠を使うのは `status='published'` だけ)。現在 D1 に draft が 2,291 曲あるので、
`--all --status published` を一度打つだけで 22 倍の違反になる。だから上限は
**サーバ側**で持っている:

- `routes/lyrics.ts` の `PUBLISHED_SONG_LIMIT = 100`。101 曲目の PUT を 409 で拒む。
- `GET /admin/lyrics/quota` で残り枠が見える。`push_lyrics.py` は published を
  含む実行の前にこれを引いて、残り枠より多ければ警告する。
- ⚠️ **この定数を上げても許諾は広がらない。** 曲数を増やすには JASRAC への区分変更が先。

**2. ストリーム形式 = 一括ダウンロードさせない。**
歌詞本文は D1 にしか置かない。`db/master.sql` / 同梱 `master.sqlite` / CloudKit の
どれにも入れない。1 リクエスト 1 曲、応答は `Cache-Control: no-store`。
まとめ取りの口 (配列パラメータ・バッチ POST) を後から足さないこと。

**3. 許諾マークと許諾番号を掲示する。**
> 「通常2週間ほどで、許諾番号・許諾マークをメールでお送りします。」
> 「お申込みいただいたサイトのトップページ等の見やすい位置に表示してください。」
> — <https://www.jasrac.or.jp/users/internet/procedure-nbusiness/>

アプリでは `JASRACLicenseNotice` が情報画面と歌詞画面に出す。
**マーク画像は JASRAC からメールで届いたものを使う。自作しない**
(それらしい画像を作るのは許諾の証明ではなく偽装)。
`Assets.xcassets` に `jasrac_mark` の名前で入れると自動的に出る。
未配置の間は許諾番号だけが出る。

### 掲載する 100 曲の選び方

`setlist_items` の披露回数の多い順に、`links.tsv` の `confidence=high` だけを採る。

- **披露回数順**にするのは、このアプリの歌詞がコールガイドだから。ライブで実際に
  よく歌われる曲ほど価値がある。上位 100 曲 (曲数の 3.2%) で**全披露の 23%** を覆う。
- **high だけ**にするのは、`low` は歌詞ページの取り違えが否定できず、`cover` は
  外国作品が混じりうるため。JASRAC は「外国作品の歌詞・楽譜の利用をする場合」
  「非商用配信の取扱いが出来かねます。」としている。
  (`cover` 56 曲の中に `ReawakeR (feat. Felix of Stray Kids)` のような要確認のものがある)
- `not_found` は本文が無いので対象外。

### まだ確認できていないこと

- **100 曲を入れ替えてよいか。** サーバは draft に戻せば枠が空く作りにしてあるが、
  年間で延べ 100 曲を超えた場合に区分内に収まるのかは許諾書から読み取れない。
  入れ替え運用を始める前に JASRAC に確認すること。
  (`song_lyrics.first_published_at` は入れ替えても初回公開時刻が残るようにしてある)

## 1. まず確認すべきこと — 本当に「非商用配信」か

**これが手続き全体の前提。ここを外すと作った報告ファイルごと無駄になる。**

手引き P.6 §2-1 の定義:

- **商用配信** — 情報料又は広告料等収入を得て行う配信、及び収入の有無にかかわらず
  営利を目的とする者が行う配信。**株式会社等が行う利用はすべて商用配信。**
- **非商用配信** — 非営利団体又は非営利の任意のグループ若しくは個人が
  営利を目的とせず行う配信。

判定に効く点 (P.7 の用語定義):

| 条件 | 区分 |
|---|---|
| アプリ内課金がある | **商用**。「情報料」はコンテンツ利用料・会費等いずれの名義でも該当 |
| 広告収入・アフィリエイトがある | **商用**。「広告料等収入」は名義を問わない |
| 収入ゼロだが法人 (株式会社等) が運営 | **商用** |
| 個人事業主が自分の事業/所属会社を紹介するサイト | **商用** |
| 市販音源 (商業用レコード等) を配信 | 収入がなくても**商用とみなす** |
| 着信音 | 収入がなくても**商用とみなす** |

ImasLiveDB の現状 (2026-08-05 時点で確認):

- 広告 SDK の導入なし。
- StoreKit は `AboutView.swift` で `requestReview` (App Store レビュー依頼) に
  使っているだけで、**課金プロダクトは存在しない**。
- IAP の entitlement も `project.yml` に設定なし。
- 個人開発の無料アプリ。

以上から非商用配信に該当する見込み。ただし**最終判断は JASRAC 側**なので、
申請時に運営形態を正確に申告すること。
**課金や広告を入れた時点で商用配信に切り替わる** (許諾番号の桁数から報告様式まで
変わる) ので、収益化を検討する際は必ずここに戻ること。

許諾番号の桁数も区分で違う: **非商用は10桁、商用は16桁**。

## 2. JASRAC 作品コード

出典: <https://j-opus.jasrac.or.jp/opus/popup/sakuhincode_help.html> と手引き P.7 §2-1-(13)

- **全体で8文字**。1桁目=数字、2桁目=数字または英大文字、3〜8桁目=数字。
- よく言われる「8桁+チェックデジット」は**誤り**。`XXX-XXXX-X` というハイフン表示は
  8文字を区切っているだけで、末尾も8文字目そのもの。
  チェックデジットの計算方法は公式に非公開で、一次ソースでは裏付けられない。
- **内外区分 = 左から2桁目がアルファベットなら外国作品** (手引き P.7 で明記)。
  ただし手引き自身が「**内外区分は途中で変更されることもある**」と注意している。
  JASRAC 側の正は請求明細データの「作品内外区分」(内国="1"、外国="2"、P.30)。
- 報告時は**ハイフン不要**。**前ゼロの桁落ちに注意** (P.20/P.27)。
  表計算ソフトを経由すると `01234567` が `1234567` になる事故が起きる。
  `build_reports.py` は7桁数字を「前ゼロが落ちた疑い」として弾く。

> **要確認**: 「外国作品は非商用配信の対象外」という理解の裏は取れていない。
> 手引きが述べているのは内外区分の判定方法と、区分によって扱いが変わることまで。
> 外国作品を報告対象から落とす実装にはしていない (フラグを立てるだけ)。
> 実際の扱いは JASRAC に直接確認すること。

## 3. 作品コードの入手手段 — 一括取得ルートは実質ない

### J-WID (作品データベース検索)
<https://www2.jasrac.or.jp/eJwid/>

検索前の了承画面に以下がある (原文):

- 「**自動Script等による検索は実行しないでください。**
  セキュリティの必要上、予告なくアクセスを遮断する場合があります。」
- 「このデータベースの**全部または一部について、承諾を得ることなしに無断で複写、
  複製、転載することは、法律で禁じられています。**」

したがって:

- **スクレイピングによる自動照合ツールは作らない。** 明示的に否定されている。
- 検索結果を蓄積して再配布する行為も無断複製・転載に抵触する。
- **CSV 等のエクスポート機能は公式に存在しない。**
- J-WID には独立した「利用規約」文書はなく、この了承画面が唯一の利用条件。

`tools/jasrac/build_reports.py form` は、人が J-WID を引くための
ワークシートを出すところまでで止めてある。

### 作品データベースの提供に関する特約
手引き P.15。JASRAC 作品データベースの一部をテキストファイル化したもの、毎月更新。

- **インタラクティブ配信の「基本契約」締結が前提**で、基本契約は**商用配信の手続き**。
  非商用配信ではこのルートは使えない可能性が高い。
- 収録は全作品ではなく「インタラクティブ配信でよく利用される楽曲」の一部。
- 料金は公式に明記なし。

### 公開 API
**存在しない。**

### 結論
非商用配信では作品コードの一括入手手段が公式に用意されていない。
そして**手引き P.20 は作品コードを「不明の場合ブランク可」としている**
(FAQ 1479 も同旨)。2,685曲を人力で J-WID 照会するより、
**作品コードはブランクで報告し、原題名・作詞者名・作曲者名で特定させる**方が現実的。

## 4. 年次利用曲目報告のファイル仕様

手引き P.24-25 (非商用配信)。項目表 P.19-20 は**商用/非商用/DL/ストリーム共通**。

- 形式: **タブ区切りテキスト (.txt)**
- 文字コード: **SJIS**
- 改行: **CR+LF** (又は CR)、各レコード末尾に必ず改行
- ファイル名: `許諾番号(10桁) + 報告年月(YYYYMM) + 任意の文字列(英数字のみ)` + `.txt`
  例: `J123456789201207.txt` — 許諾番号 `J123456789` のように**英字を含む10文字**。
  「10桁」は数字10個の意味ではないので、実装も英数字10文字で検証している。
- まとめ単位: 許諾ごとに1ファイル
- 提出先: J-TAKT <https://j-takt.jasrac.or.jp/> →「利用曲目のご報告［J-NOTES］」
- 期限: 更新月または満了月の翌月末日 (JASRAC からの案内メール後)
- **利用回数が0回の楽曲も報告は必須** (P.25 注3)

### 報告データ項目表 (19項目・この順序)

タブの数が18未満だとエラー (P.26 項番1) = **19項目ちょうどで固定**。
凡例: M=必須、M*=いずれか必須、C=条件付き必須、O=任意。桁数は**バイト数**(日本語2バイト)。

| # | 項目名 | 必須 | 桁 | 本プロジェクトでの値 |
|---|---|---|---|---|
| 1 | インターフェイスキーコード | M | 30 | `imasdb-<sha1(song_id)[:12]>` で新規発行し、**works.tsv に永続化**。使用可能文字は `0-9a-zA-Z@-._`+半角スペース |
| 2 | コンテンツ区分 | C | 1 | ブランク (1コンテンツ1楽曲) |
| 3 | コンテンツ枝番 | M | 3 | `000` |
| 4 | メドレー区分 | C | 1 | ブランク |
| 5 | メドレー枝番 | M | 3 | `000` |
| 6 | コレクトコード | C | 1 | **常に空欄。ただし欄ごと削除するとエラー** (P.25) |
| 7 | ＪＡＳＲＡＣ作品コード | C | 8 | 不明ならブランク可 |
| 8 | 原題名 | M | 200 | できるだけ J-WID 上の記述にそろえる |
| 9 | 副題・邦題 | O | 60 | |
| 10 | 作詞者名 | M* | 250 | 複数は**全角スラッシュ「／」区切り** |
| 11 | 補作詞・訳詞者名 | O | 60 | |
| 12 | 作曲者名 | M* | 250 | 作詞者名といずれか必須 |
| 13 | 編曲者名 | O | 60 | |
| 14 | アーティスト名 | O | 100 | 任意項目なので、SJIS 外の文字は除去し100バイトで切る。均した件数は実行時に表示 |
| 15 | 情報料（税抜） | M | 13 | `0` (無料)。数字のみ、カンマ不可 |

| 18 | ＩＬ区分 | C | 1 | ブランク (CD音源配信ではない) |
| 19 | リクエスト回数 | C | 9 | `0` (集計不可能な場合)。数字のみ、カンマ不可 |

## 5. ツールの使い方

JASRAC 情報は `songs` テーブルに列を足さず `tools/jasrac/works.tsv` で別管理する。
アプリが表示しない管理データなので、CloudKit スキーマや iOS/Android のモデルに
波及させる理由がない。

ファイル構成:

| ファイル | 役割 |
|---|---|
| `works_tsv.py` | 台帳のスキーマと入出力。両スクリプトの唯一の契約 |
| `extract_works.py` | master.sqlite → 照合台帳 `works.tsv` |
| `build_reports.py` | `works.tsv` → 提出物 |

```bash
# 集計だけ見る (書き込まない)
python3 tools/jasrac/extract_works.py

# 照合台帳 works.tsv を生成/更新 (手入力列は保持される)
python3 tools/jasrac/extract_works.py --apply

# 不足項目の洗い出し → out/gaps.tsv
python3 tools/jasrac/build_reports.py gaps

# J-WID を人手で引くためのワークシート (100件ずつ) → out/form_NNN.tsv
python3 tools/jasrac/build_reports.py form --unmatched-only

# 年次利用曲目報告 → out/<許諾番号><YYYYMM>.txt
python3 tools/jasrac/build_reports.py annual --license-no J123456789 --month 202608
```

`master.sqlite` は `.gitignore` 対象なので、無ければ `db/master.sql` から自動生成する
(`tools/apply_data.py` と同じ作法)。

`works.tsv` の手入力列 (`extract_works.py` を再実行しても保持):

| 列 | 用途 |
|---|---|
| `interface_key` | 報告項目1。**一度発行したら振り直さない**ため台帳が保持する |
| `jasrac_code` | J-WID で確認した8文字の作品コード |
| `jasrac_title` | J-WID 上の作品名。**埋めると SJIS 変換エラーが解消する** |
| `match_status` | 下表の5値。誤記は読み込み時に警告 |
| `note` | 判断の根拠メモ |

`match_status` の語彙:

| 値 | 意味 |
|---|---|
| `unmatched` | 未照合 (既定値) |
| `matched` | J-WID で作品コードを確定 |
| `ambiguous` | 同名異曲が複数あり確定できない |
| `not_found` | J-WID に見つからない |
| `excluded` | **JASRAC 管理外と確認済み**。報告母集団から外す |

`excluded` は報告漏れの温床になるので、根拠 (自主制作・PD 等) を `note` に必ず書く。
手引き P.25 注3 は「利用回数が0回の楽曲についても報告は必ずしてください」としており、
**利用していないことは除外の理由にならない**。

`annual` は提出前チェックを通してからでないと書き出さない。
チェック内容は必須項目・条件付き必須・書式・SJIS 変換可否・バイト長で、
すべて `build_reports.py` の `ANNUAL_SPEC` (上の項目表そのもの) から導かれる。
`--force` で書き出すこともできるが、その場合 SJIS 変換できない文字は `?` に
置換されるため、`jasrac_title` を埋めて解消するのが本筋。

## 6. 現状のデータギャップ (2026-08-05 時点、2,685曲)

`python3 tools/jasrac/build_reports.py gaps` で再集計できる。

要対応 406 レコード / 418 件。

| 問題 | 件数 | 対処 |
|---|---|---|
| 作詞者・作曲者がどちらも空 | 345 | **提出不可**。項目10/12 はいずれか必須。要データ拡充 |
| 原題名が SJIS 変換不可 | 44 | `jasrac_title` に J-WID 表記を入れる |
| 作曲者名が SJIS 変換不可 | 13 | J-WID 表記に直す |
| 作詞者名が SJIS 変換不可 | 9 | 同上 |
| 副題が SJIS 変換不可 | 7 | 同上 |

アーティスト名は任意項目なので自動で均され、エラーには出ない (140件が対象)。

作詞作曲が空の345曲の内訳は cover 142 / unit 113 / solo 72 / all 17 / tie_in 1。
カバー曲142曲は全曲が空なので、ここを埋めるのが最優先。

SJIS で落ちる主な文字: `♡` (U+2661)、`É`/`é`、ハングル、`Ø`、`ゔ` (U+3094)、`✿`、`⬆`。
`765as_pingpong_game` の作家名がハングル (`Gamenrider[서용배…]`) なのは
**外国作品登録の強いシグナル**。作品コードの2桁目を確認すること。

### 版違いの判定と、そこで露出した表記ゆれ

版違い (REM@STER / Remix 等) は**キーワードを列挙せず**、
「末尾を剥がした結果が他の曲のタイトルと一致するか」という構造で判定している
(`extract_works.py: split_title`)。`FO(U)R` や `千夜一夜(Alf Layla wa Layla)` の
ように括弧が作品名の一部であるケースを誤って割らないのが利点。

この方式にしたことで、master.sqlite 側の表記ゆれが 6 件露出した
(原作品が見つからないため版違いと判定されない):

| 版違い側の表記 | 原作品側の表記 | ずれ |
|---|---|---|
| `ポジティブ(REM@STER-B)` | `ポジティブ！` | `！` の有無 |
| `ポジティブ！!(REM@STER-A)` | `ポジティブ！` | `!` の重複 |
| `私はアイドル(REM@STER-A)` | `私はアイドル♡` / `私はアイドル♥` | `♡` の有無 |
| `隣に・・・ -JAZZ Rearrange Mix-` | `隣に…` | 中黒3つ vs 三点リーダ |
| `チョー⬆元気Show☆アイドルch@ng! (Giga Remix)` | `チョー↑元気Show☆アイドルch@ng!` | `⬆` vs `↑` |
| `微笑んだから、気づいたんだ（KAN TAKAHIKO Remix）` | `微笑んだから、気づいたんだ。` | 句点の有無 |

これらは J-WID 照合でも同じ問題を起こすので、master.sqlite 側を直すのが本筋。
