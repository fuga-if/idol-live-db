# tools/lyrics — 歌詞と歌詞リンクの作業ツール

## 1. 歌詞リンクの収集 (継続作業)

`songs.lyrics_url` を埋めて、曲詳細から歌詞サイトへ飛べるようにする。
リンクは掲載ではないので JASRAC 許諾は不要。

### なぜセッションを跨ぐのか

**WebSearch はセッション全体で 200 回が上限で、エージェント間で共有される。**
並列に増やしても総量は変わらない。全 2,685 曲には同数の検索が要るので、
12〜13 セッションに分けて進める。

歌ネットは `robots.txt` が 403 を返し自動アクセスを拒否しているので、
**サイトを直接叩かない**。URL の発見は検索エンジンの結果からのみ行う。

### 再開手順

```bash
# 1. 未調査分をスライスに切り出す (既存の候補は自動で対象から外れる)
python3 tools/lyrics/link_worklist.py --slices 150

# 2. エージェントに slice_01 から順に処理させる (1セッションで 150〜200曲が限度)
#    出力は tools/lyrics/slices/out_NN.tsv に
#      song_id / candidate_url / candidate_title / note
#    見つからない曲は URL を**空欄**にすること。文言を書かない。
#
#    ⚠️ **「検索したが見つからなかった」と「予算切れで未着手」を必ず区別させること。**
#       未着手の行は note に「未着手」と書かせる。書かせないと、マージ時に
#       not_found を立ててしまい、次回のスライスから漏れて永久に調査されない。

# 3. 回収した候補を links.tsv にマージし、機械判定を回す
python3 tools/lyrics/link_verify.py --apply

# 4. high だけを data/fixes の JSON に書き出す
python3 tools/lyrics/export_links_json.py --apply

# 5. 反映
python3 tools/apply_data.py --check
python3 tools/apply_data.py --apply
```

スライスは**セトリ登場回数の多い順**なので、`slice_01` から埋めるのが効率的。
実用上は上位数百曲で足りる。

### 判定の考え方 (`link_verify.py`)

キャスト構成が違っても歌詞は同じなので、版や人数の一致は要求しない。
避けたいのは**同名の全く別の曲**を掴むことだけ。判定条件は 2 つ:

1. 候補ページのタイトルに曲名が含まれる
2. 候補ページのタイトルにアイマス関連の固有名詞が含まれる
   (アイドル名・声優名・ユニット名・ブランド名を master.sqlite から集めた 2,236 語)

`high` だけを `lyrics_url` に昇格させる。

## 2. 歌詞本文の投入

**JASRAC の許諾が下りるまで公開しない。** 詳細は `docs/JASRAC.md` §0。

```bash
# テキストを貼って登録 (lyrics_local/ は gitignore 済み)
python3 tools/lyrics/add_lyrics.py "曲名" --clipboard
python3 tools/lyrics/lyrics_json.py validate

# D1 へ投入 (既定は draft。公開には --status published が要る)
python3 tools/lyrics/push_lyrics.py --all --apply
```

歌詞本文は `data/fixes/` に**置かない**。あそこは公開 git リポジトリ。

## 3. プチリリとの照合 (誤りの洗い出し)

取り込み元由来の誤り (♡ 等の記号の欠落、中国語行の表記崩れ) を見つけるために、
歌詞投稿サイト**プチリリ** (petitlyrics.com) の歌詞と突き合わせて差分を出す。

**本文の自動書き換えはしない。** 差分を報告するところまでで、直すかどうかは人が
判断する。プチリリ側にも誤りはある (下の「精度」参照) ので、鵜呑みにできない。

```bash
# 1. 候補を集める。**アーティスト一覧を辿る list を使う** (検索は下記の理由で使えない)
python3 tools/lyrics/petitlyrics_check.py list --limit 200

# 2. high の候補の本文を取得してキャッシュ
python3 tools/lyrics/petitlyrics_check.py fetch

# 3. 手元の歌詞と突き合わせて報告
python3 tools/lyrics/petitlyrics_check.py diff
python3 tools/lyrics/petitlyrics_check.py diff --only 765as_ready
```

`search` サブコマンドも残してあるが、**検索ページは数件で長時間の制限に入る**ので
実用にならない (下記)。候補集めは `list` を使うこと。

出力 (いずれも gitignore 済み。歌詞本文はここから外に出さない):

| パス | 中身 |
|---|---|
| `lyrics_local/petitlyrics/candidates.tsv` | song_id / petit_id / title / artist / confidence / note |
| `lyrics_local/petitlyrics/artists.json` | artist_id → アーティスト名 (50音索引 71ページから作る) |
| `lyrics_local/petitlyrics/pages/` | 取得した一覧ページの gzip キャッシュ。再取得しない |
| `lyrics_local/petitlyrics/<song_id>.json` | 取得した本文のキャッシュ |
| `tools/lyrics/out/petitlyrics_report.tsv` | 差分レポート |

候補の判定条件は歌詞リンク収集 (§1) と同じ 2 つ — 曲名が一致し、かつ歌手名に
アイマス関連の固有名詞が含まれること。実装も `link_verify.py` を import して共用する。

### 検索ページには厳しいアクセス制限がある (重要)

プチリリの**検索ページ**は、少し叩くと 403 でも空の結果でもなく、
**HTTP 200 で「歌詞検索ページへのアクセスが多いため一時的に非表示にしています。
しばらく経ってからアクセスして下さい。」と書いたページ**を返すようになる。

これを「0 件見つかった」と読むと、**調査済みだが見つからなかった**という誤った記録が
`candidates.tsv` に残り、その曲は二度と調査されない。§1 の「未着手と not_found を
必ず区別する」とまったく同じ罠なので、`search` は制限を検出したら**その場で打ち切り、
何も記録しない**。時間を置いて同じコマンドを再実行すれば続きから進む。

- 本当の結果ページには「N 件見つかりました」がある。これが目印。
- **判定は必ず `html.unescape()` してから。** プチリリは日本語を数値文字参照で吐くので、
  生 HTML を検索しても「件見つかりました」も制限の文言も絶対に一致しない。
- 実測 (2026-09-04): 連続検索は **5 件で制限に当たった**。`--interval` の既定を 8 秒に
  してあるが、それでも上限は低い。**歌詞本文の取得 (`fetch`) の側は制限されていない。**

### 歌詞本文の取り方 (実測)

本文は `<canvas id="lyrics">` に描かれるので HTML には載っていない。
`POST /com/get_lyrics.ajax` (form `lyrics_id=<id>`) が
`[{"lyrics":"<base64 UTF-8>"}, ...]` を返す (1 要素 = 1 行、空行は `""`)。暗号化はない。
罠が 3 つある:

1. **`X-CSRF-Token` が要る。** トークンはページ HTML ではなく、セッションごとに生成される
   `/lib/pl-lib.js?<timestamp>` の中に書かれている。ページ GET → pl-lib.js GET →
   32 桁 hex、の順で拾う。
2. **ヘッダ名の大文字小文字が区別される。** `X-CSRF-Token` でなければ 400。
   `urllib.request` は送信時に必ず `.title()` を掛けて `X-Csrf-Token` にしてしまうため、
   **urllib では原理的に成功しない**。`http.client` を直に使うこと。
   (curl では通るのに urllib だけ 400、という形で現れる)
3. Cookie (`PLSESSION`) をページ取得時から引き回す。

`robots.txt` は 404 (記述なし)。それでも 1 リクエスト 1.5 秒以上・同時 1 接続を守る。

### 比較は行単位ではなく本文全体で行う

プチリリはカラオケ同期サイトなので、**1 行が同期の単位で切られている**。
「ほら見て　ステキな出会いの予感の青い空」がこちらでは 1 行、あちらでは 2 行、
というだけの違いが大量に出て、本当に見たい記号や文字の誤りがその中に埋もれる。

そこで**空白を落として全行を連結した 1 本の文字列**として比べる。行の切り方の違いは
最初から消え、残るのは文字と記号の違いだけになる。判定は 4 つ:

| verdict | 意味 |
|---|---|
| `一致` | 空白を除いて完全一致 |
| `記号差のみ` | 文字と数字は同じで記号だけ違う (♡ の欠落など。**主目的**) |
| `文字差` | 文字そのものが違う |
| `大差` | 一致率が低い。書き起こしの誤りではなく別バージョンの疑い |

### 精度 (2026-09-04、披露回数上位 50 曲のうち検索が通った 5 曲)

`一致` 2 / `文字差` 3。差分 8 件の内訳を人が見た結果:

- **プチリリ側の誤り 2 件** — `ENTERTAINMEN` (T 欠落)、`理田(ワケ)` (由 → 田)。
- **こちらのルビ表記 2 件** — `行(ゆ)けば` ↔ `行けば`。手元がルビを括弧で持っている分
  (同じ曲で 2 箇所)。
- **漢字/かなの表記ゆれ 2 件** — `掴もう`↔`つかもう`、`掴み取る`↔`掴みとる`。
- **記号の有無 1 件** — `PEACE?` の `?`。
- **プチリリ側だけにある掛け声 1 件** — `(もう一回!)`。

つまり**プチリリは正解ではなく「second opinion」**。差分は当たりを付けるためのもので、
最終的な可否は公式ブックレット等で人が確認する。ルビの括弧はこちらの仕様なので、
`文字差` に必ず混ざるノイズとして読み飛ばしてよい。

### 候補集めは一覧ページを辿る (`list`)

検索が使えないので、**アーティスト歌詞一覧**を辿って petit_id を集める。
この経路は制限に入らないことを実測で確認した。

```
/syllabary/<kana>.html          アーティスト50音索引。全71ページ、計 71,064件の
                                (artist_id, アーティスト名) が取れる
/lyrics/artist/<id>             そのアーティストの歌詞一覧 (10件/ページ)
/lyrics/artist/<id>/<n>-1.html  2ページ目以降
```

アルバム一覧 `/lyrics/album/<アルバム名の UTF-8 hex>` も同じ形式で使えるが、
**master.sqlite の `cd_title` は公開曲 3,153 件中 378 件しか埋まっておらず**、
中身も `…シリーズ#MS2P` のような内部表記でアルバム名にならないので使えない。
`singer_label` は 2,386 件埋まっているので、アーティスト経路を採る。

### 50音索引は網羅していない — この経路の上限 (重要)

`/syllabary/<kana>.html` は**全アーティストを載せていない**。実測 (2026-09-04):

- 索引から集まるのは 71,064 件。`ta.html` のアーティストリンクは 1,644 件しかない。
- `キラメキラリ` はプチリリに 33 件あり、名義は「高槻やよい (仁後真耶子)」。
  ところが**この名義は索引に無い** (索引で `高槻やよい` を含む 37 名義は全ページ
  取得済みだが、その中に無い)。つまり索引から辿れないアーティストがいる。

このため**アーティスト経路には構造的な上限がある**。実測では上位200曲のうち
87曲で頭打ちになり、語彙を全体に広げて 1,107 名義を追加で辿っても**新規は2曲**
だった (`--broad`)。残りは索引に載っていない名義に紐づいている。

残りを埋めるなら、検索ページを**持続可能なレートで**使う経路を確かめるしかない
(制限は連続5件で発動し、解除まで50分以上かかることまでは分かっている)。

**辿る順番が効く。** プチリリのアーティスト名は
「天海春香(中村繪里子),如月千早(今井麻美),…」のような曲ごとのクレジット文字列なので、
対象曲のアイドル名を多く含む名義ほど当たりやすい。名前の短い個人名義から辿ると
空振りが続く (実測: その順で先頭80件を辿って 23曲しか付かなかった)。

### 差分の仕分け (`kinds` 列)

差分1件ずつを6分類する。**どちらが正しいかは判定しない** — 人が見るときの
当たりを付けるだけ。

| 分類 | 意味 |
|---|---|
| `記号欠落(手元)` | プチリリにあって手元に無い記号。**今回探しているもの** |
| `間奏記号(無視)` | プチリリ側にだけある `♪` (単独・連続とも)。カラオケ同期用の間奏記号であって歌詞ではないので補完しない。`☆` や `!` は対象のまま |
| `記号余分(手元)` | 逆に手元にだけある記号 |
| `記号差` | 双方に別々の記号がある |
| `漢字かな` | 片方が漢字、片方が同じ読みのかな |
| `ルビ` | `行(ゆ)けば` のような手元のルビ括弧。こちらの仕様なのでノイズ |
| `コール` | `(もう一回!)` のような掛け声 |
| `プチリリ側誤字` | 1文字だけ違う/落ちている形 |
| `不明` | 上記に当てはまらない |

### 実測 (2026-09-04、披露回数上位200曲のうち候補が付いた87曲)

| verdict | 曲数 |
|---|---|
| 一致 | 30 |
| 記号差のみ | 8 |
| 文字差 | 30 |
| 大差 | 19 |

差分 424 件の内訳: 不明 153 / 記号差 140 / 漢字かな 42 / ルビ 39 /
プチリリ側誤字 25 / 間奏記号(無視) 14 / コール 5 / **記号欠落(手元) 3** / 記号余分(手元) 3。

**手元から落ちている記号を実際に検出できた。** ただし当初 17件あった
`記号欠落(手元)` のうち 14件は `arcadia` の `♪♪♪` のような間奏記号だったので
除外し、残る本物の欠落は **3件** (`メルヘンデビュー！` の `☆` 2件、
`MEGARE!` の `!` 1件)。当初報告の `♡` はこの87曲には含まれていなかった。

`大差` 19曲は書き起こしの誤りではなく、プチリリ側が別バージョン (尺違い・
ライブ版) を載せているケースが大半。人が見る優先度は低い。

## 4. 歌ネットに無かった曲をプチリリから入れる (`import`)

`songs.lyrics_url` が埋まらなかった曲 (歌ネットに無い) を、プチリリ由来の本文で埋める。

```bash
# 対象曲リスト (song_id / 曲名 / 歌唱 の3列) から候補を集める
python3 tools/lyrics/petitlyrics_check.py list --targets targets.tsv --max-artists 700

# 本文を取得
python3 tools/lyrics/petitlyrics_check.py fetch

# lyrics_local/lyrics/<song_id>.json を作る (--apply なしは何も書かない)
python3 tools/lyrics/petitlyrics_check.py import --targets targets.tsv --apply
python3 tools/lyrics/lyrics_json.py validate
```

### 採用の条件は緩めない

`match_target()` の2条件を**両方**満たす候補だけを採る:

1. 曲名が**完全一致** (NFKC・空白無視・大小無視)。`(M@STER VERSION)` のような
   版名つきは採らない。
2. アーティスト名に、その曲の**歌唱アイドル名かユニット名**が含まれる。

同名異曲や尺違いを掴むと誤った歌詞がそのまま公開されるので、ここを緩めないこと。
条件に通らないものは候補一覧に残して人が見る。

### 行の落とし込み

`lyrics_json.text_to_lines` に渡す前に整形する:

- 空行はそのまま (段落の余白として解釈される)
- **`♪` だけの行は間奏記号なので本文に入れない。** 空行2つに置き換えて間奏マーカーに
  させる。`<♪>` `(♪)` `（♪）` のように括弧で囲った形もあるので、裸の `♪` だけを
  見ていると取りこぼす (実測で2曲が検証に引っかかった)

`source` は `プチリリ <petit_id> (投稿者名)`、`note` は `歌ネットに無し・プチリリ由来`。
**手元に既に歌詞がある曲は書き換えない** (import が skip する)。

## 5. 版違いは親の歌詞を流用する (`copy_variants.py`)

REM@STER / Remix / rearrange / Game Size のような**版違いは歌詞が同じ**なので、
プチリリから取り直さず親 (`songs.parent_song_id`) の歌詞をそのまま使う。

```bash
python3 tools/lyrics/copy_variants.py            # 件数と除外一覧を見るだけ
python3 tools/lyrics/copy_variants.py --apply
python3 tools/lyrics/push_lyrics.py $(cat ids.txt) --status published --apply
```

対象は「親が公開済み・自分は未公開・手元に JSON が無い」曲のうち、
**タイトルの本体部分が親と一致する**ものだけ。`parent_song_id` は人手で入るので
別曲が親になっている取り違えがありうる。版名の剥がし方は `link_verify.base_title`
を共用する。

`strict_key` は NFKC に加えて**約物の字形も揃える**。NFKC は `’` (U+2019) を `'` に
直さないので、これが無いと `Parade d’amour` と `Parade d'amour (les amis d'enfance ver.)`
が別曲扱いで弾かれる (実測)。

### D1 への投入は間隔を空ける

445曲を一気に PUT したら **132曲が HTTP 503 (Cloudflare error 1102)** で落ちた。
2秒あけて投げ直したら全件通ったので、まとめて入れるときは間隔を空けること。

## 6. 検索ページの実測 (2026-09-04 追試)

90秒間隔・1件ずつなら**遮断されない**。1.5秒間隔だと5件で遮断され解除に50分以上
かかっていたので、間隔がそのまま効く。

**0件ページを遮断と誤判定しないこと。** 結果ページの目印は「N 件見つかりました」だが、
0件のときは代わりに「**検索結果がありません**」が出る。これを見落とすと、遮断されて
いないのに走行が止まる (実測: `Don't U Worry` の検索で4件目に誤って打ち切った)。
