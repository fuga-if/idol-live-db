# tools/lyrics — 歌詞と歌詞リンクの作業ツール

## 1. 歌詞リンクの収集 (継続作業)

`songs.lyrics_url` を埋めて、曲詳細から歌詞サイトへ飛べるようにする。
リンクは掲載ではないので JASRAC 許諾は不要。

### なぜセッションを跨ぐのか

**WebSearch はセッション全体で 200 回が上限で、エージェント間で共有される。**
並列に増やしても総量は変わらない。全 2,685 曲には同数の検索が要るので、
12〜13 セッションに分けて進める。

歌ネットは `robots.txt` が 403 を返し自動アクセスを拒否しているので、
**サイトを直接叩かない**。URL の発見は検索エンジンの結果からのみ行う。

### 再開手順

```bash
# 1. 未調査分をスライスに切り出す (既存の候補は自動で対象から外れる)
python3 tools/lyrics/link_worklist.py --slices 150

# 2. エージェントに slice_01 から順に処理させる (1セッションで 150〜200曲が限度)
#    出力は tools/lyrics/slices/out_NN.tsv に
#      song_id / candidate_url / candidate_title / note
#    見つからない曲は URL を**空欄**にすること。文言を書かない。
#
#    ⚠️ **「検索したが見つからなかった」と「予算切れで未着手」を必ず区別させること。**
#       未着手の行は note に「未着手」と書かせる。書かせないと、マージ時に
#       not_found を立ててしまい、次回のスライスから漏れて永久に調査されない。

# 3. 回収した候補を links.tsv にマージし、機械判定を回す
python3 tools/lyrics/link_verify.py --apply

# 4. high だけを data/fixes の JSON に書き出す
python3 tools/lyrics/export_links_json.py --apply

# 5. 反映
python3 tools/apply_data.py --check
python3 tools/apply_data.py --apply
```

スライスは**セトリ登場回数の多い順**なので、`slice_01` から埋めるのが効率的。
実用上は上位数百曲で足りる。

### 判定の考え方 (`link_verify.py`)

キャスト構成が違っても歌詞は同じなので、版や人数の一致は要求しない。
避けたいのは**同名の全く別の曲**を掴むことだけ。判定条件は 2 つ:

1. 候補ページのタイトルに曲名が含まれる
2. 候補ページのタイトルにアイマス関連の固有名詞が含まれる
   (アイドル名・声優名・ユニット名・ブランド名を master.sqlite から集めた 2,236 語)

`high` だけを `lyrics_url` に昇格させる。

## 2. 歌詞本文の投入

**JASRAC の許諾が下りるまで公開しない。** 詳細は `docs/JASRAC.md` §0。

```bash
# テキストを貼って登録 (lyrics_local/ は gitignore 済み)
python3 tools/lyrics/add_lyrics.py "曲名" --clipboard
python3 tools/lyrics/lyrics_json.py validate

# D1 へ投入 (既定は draft。公開には --status published が要る)
python3 tools/lyrics/push_lyrics.py --all --apply
```

歌詞本文は `data/fixes/` に**置かない**。あそこは公開 git リポジトリ。

## 3. プチリリとの照合 (誤りの洗い出し)

取り込み元由来の誤り (♡ 等の記号の欠落、中国語行の表記崩れ) を見つけるために、
歌詞投稿サイト**プチリリ** (petitlyrics.com) の歌詞と突き合わせて差分を出す。

**本文の自動書き換えはしない。** 差分を報告するところまでで、直すかどうかは人が
判断する。プチリリ側にも誤りはある (下の「精度」参照) ので、鵜呑みにできない。

```bash
# 1. 披露回数の多い順に曲名で検索し、候補を記録 (小さいバッチで回す)
python3 tools/lyrics/petitlyrics_check.py search --limit 50

# 2. high の候補の本文を取得してキャッシュ
python3 tools/lyrics/petitlyrics_check.py fetch

# 3. 手元の歌詞と突き合わせて報告
python3 tools/lyrics/petitlyrics_check.py diff
python3 tools/lyrics/petitlyrics_check.py diff --only 765as_ready
```

出力 (いずれも gitignore 済み。歌詞本文はここから外に出さない):

| パス | 中身 |
|---|---|
| `lyrics_local/petitlyrics/candidates.tsv` | song_id / petit_id / title / artist / confidence / note |
| `lyrics_local/petitlyrics/<song_id>.json` | 取得した本文のキャッシュ |
| `tools/lyrics/out/petitlyrics_report.tsv` | 差分レポート |

候補の判定条件は歌詞リンク収集 (§1) と同じ 2 つ — 曲名が一致し、かつ歌手名に
アイマス関連の固有名詞が含まれること。実装も `link_verify.py` を import して共用する。

### 検索ページには厳しいアクセス制限がある (重要)

プチリリの**検索ページ**は、少し叩くと 403 でも空の結果でもなく、
**HTTP 200 で「歌詞検索ページへのアクセスが多いため一時的に非表示にしています。
しばらく経ってからアクセスして下さい。」と書いたページ**を返すようになる。

これを「0 件見つかった」と読むと、**調査済みだが見つからなかった**という誤った記録が
`candidates.tsv` に残り、その曲は二度と調査されない。§1 の「未着手と not_found を
必ず区別する」とまったく同じ罠なので、`search` は制限を検出したら**その場で打ち切り、
何も記録しない**。時間を置いて同じコマンドを再実行すれば続きから進む。

- 本当の結果ページには「N 件見つかりました」がある。これが目印。
- **判定は必ず `html.unescape()` してから。** プチリリは日本語を数値文字参照で吐くので、
  生 HTML を検索しても「件見つかりました」も制限の文言も絶対に一致しない。
- 実測 (2026-09-04): 連続検索は **5 件で制限に当たった**。`--interval` の既定を 8 秒に
  してあるが、それでも上限は低い。**歌詞本文の取得 (`fetch`) の側は制限されていない。**

### 歌詞本文の取り方 (実測)

本文は `<canvas id="lyrics">` に描かれるので HTML には載っていない。
`POST /com/get_lyrics.ajax` (form `lyrics_id=<id>`) が
`[{"lyrics":"<base64 UTF-8>"}, ...]` を返す (1 要素 = 1 行、空行は `""`)。暗号化はない。
罠が 3 つある:

1. **`X-CSRF-Token` が要る。** トークンはページ HTML ではなく、セッションごとに生成される
   `/lib/pl-lib.js?<timestamp>` の中に書かれている。ページ GET → pl-lib.js GET →
   32 桁 hex、の順で拾う。
2. **ヘッダ名の大文字小文字が区別される。** `X-CSRF-Token` でなければ 400。
   `urllib.request` は送信時に必ず `.title()` を掛けて `X-Csrf-Token` にしてしまうため、
   **urllib では原理的に成功しない**。`http.client` を直に使うこと。
   (curl では通るのに urllib だけ 400、という形で現れる)
3. Cookie (`PLSESSION`) をページ取得時から引き回す。

`robots.txt` は 404 (記述なし)。それでも 1 リクエスト 1.5 秒以上・同時 1 接続を守る。

### 比較は行単位ではなく本文全体で行う

プチリリはカラオケ同期サイトなので、**1 行が同期の単位で切られている**。
「ほら見て　ステキな出会いの予感の青い空」がこちらでは 1 行、あちらでは 2 行、
というだけの違いが大量に出て、本当に見たい記号や文字の誤りがその中に埋もれる。

そこで**空白を落として全行を連結した 1 本の文字列**として比べる。行の切り方の違いは
最初から消え、残るのは文字と記号の違いだけになる。判定は 4 つ:

| verdict | 意味 |
|---|---|
| `一致` | 空白を除いて完全一致 |
| `記号差のみ` | 文字と数字は同じで記号だけ違う (♡ の欠落など。**主目的**) |
| `文字差` | 文字そのものが違う |
| `大差` | 一致率が低い。書き起こしの誤りではなく別バージョンの疑い |

### 精度 (2026-09-04、披露回数上位 50 曲のうち検索が通った 5 曲)

`一致` 2 / `文字差` 3。差分 8 件の内訳を人が見た結果:

- **プチリリ側の誤り 2 件** — `ENTERTAINMEN` (T 欠落)、`理田(ワケ)` (由 → 田)。
- **こちらのルビ表記 2 件** — `行(ゆ)けば` ↔ `行けば`。手元がルビを括弧で持っている分
  (同じ曲で 2 箇所)。
- **漢字/かなの表記ゆれ 2 件** — `掴もう`↔`つかもう`、`掴み取る`↔`掴みとる`。
- **記号の有無 1 件** — `PEACE?` の `?`。
- **プチリリ側だけにある掛け声 1 件** — `(もう一回!)`。

つまり**プチリリは正解ではなく「second opinion」**。差分は当たりを付けるためのもので、
最終的な可否は公式ブックレット等で人が確認する。ルビの括弧はこちらの仕様なので、
`文字差` に必ず混ざるノイズとして読み飛ばしてよい。
